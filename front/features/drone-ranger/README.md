# Drone Ranger 2D dashboard

Application-owned React workspace for reinforcement-learning policy work. Its top navigation switches between one-episode run inspection, training configuration and model editing; the former standalone demo page has been removed, and Run is the default landing page. `DroneRangerDashboard.tsx` contains the current DQN, PPO, SAC and A2C preview profiles, route samples, Canvas renderer, dropdown model selectors, decision inspection and configuration forms. `drone-ranger.css` owns its responsive presentation.

The displayed episode, rewards, routes, success rates and hyperparameters are explicitly preview data. The run page executes a deterministic frontend preview from the current navigation points, applies a small strategy-specific trace drift and reports position, heading, nearest-obstacle clearance, action, value estimate and step reward at 5% intervals. Exact waypoint and obstacle coordinates are editable in tables below the log. This is not checkpoint inference: no model runtime, simulator or live telemetry interface exists in this project yet. The model editor includes per-policy reference architecture diagrams for input shape, backbone layers, output heads, activation and approximate parameter scale; these diagrams are not parsed from checkpoints. The training page captures environment, total and per-episode timesteps, parallel rollout size, learning rate, batch size, discount, gradient clipping, evaluation cadence, evaluation episodes, checkpoint cadence, seed and device. Training settings and model edits are local, in-memory drafts and do not overwrite checkpoint/source configuration. Replace the local preview evaluator with a documented application API when real episode output is available; keep rendering independent from transport and preserve the right-side Saplingagent chat.

The Canvas uses a 1000×620 world coordinate system and scales for its container/device pixel ratio. HTML overlays provide controls and readable telemetry. Desktop places the strategy summary beside the map; narrow screens stack the map, summary, playback and parameter cards.

Mission inputs use the same world coordinate system. Users can edit waypoint coordinates plus obstacle coordinates, labels and dimensions directly in the tables below the run result. Changes are in-memory preview state only, and the run page recomputes its frontend preview trace from the edited navigation points and obstacle clearances. No simulator/training environment file is updated.

The application-local language control switches the complete dashboard and Canvas labels between English and Simplified Chinese and stores only the selected locale in browser local storage. The right-side AI chat remains a fixed overlay when expanded, so opening it never resizes the mission workspace.

Verification entry: run `npm run build` and `npm test -- --run` from `front/`, load the project page, confirm Run opens by default, switch all three workspace pages and every policy option, run a complete preview episode, inspect the decision log and edit both input tables, then exercise both local forms. A build or DOM inspection is not human acceptance of the model data or visualization. The frontend evaluator is presentation evidence only and cannot establish real model feasibility until connected to checkpoint inference or simulator output.
